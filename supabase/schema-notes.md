# Schema Notes

## ALEX-001 Assumptions

- `profiles.auth_user_id` links app identity to `auth.users.id`; workspace membership uses `workspace_members.profile_id`. `profiles.deleted_at` supports full user removal while preserving profile references used for authored-memory attribution.
- Current workspace membership is represented by the presence of a `workspace_members` row. Member removal deletes that row instead of marking a lifecycle timestamp.
- `workspaces.slug` is globally unique, and `workspaces.context_description` is required with the ADR 015 minimum of 30 trimmed characters.
- `workspaces.tier` is the manually managed v1 processing tier from ADR 012. It defaults to `basic`; no billing or signup-tier logic is modeled in the database migration.
- `workspaces.conflict_thresholds` stores the ADR 014 launch defaults: duplicate `0.97` and conflict `0.85`.
- `mcp_keys` are workspace-owned, but `key_prefix` is globally unique so API key validation can look up by prefix before checking the bcrypt `key_hash`.
- `workspace_invites.token` is the plaintext unique invite token from ADR 015. `invited_by_profile_id` and `expires_at` are non-null; `expires_at` defaults to seven days after creation. A trigger prevents more than one simultaneous active invite for the same normalized `(workspace_id, email)` while preserving accepted, revoked, and expired invite history.
- Search scaffolding includes a generated `memories.search_document` `tsvector`, a nullable unconstrained `memories.embedding` pgvector column, and workspace-leading B-tree indexes for tenant-scoped candidate filters. No search functions, rerank logic, ANN vector indexes, or worker logic are added.
- `memories.embedding` intentionally uses unconstrained `vector` storage because the locked spec names OpenAI `text-embedding-3-small` for the basic tier and Voyage 3 for the pro tier without locking a single shared dimension. Dimension-specific ANN indexes should be added with the backend processing path once per-tier/model dimensions are fixed.
- Default read indexes treat current memories as rows where `deleted_at is null` and `superseded_by_memory_id is null`. RLS still enforces tenant membership; exclusion of superseded/deleted rows remains a query concern until product read APIs are added.
- `memories.status` keeps the consolidated spec values `processing`, `active`, `conflict`, and `failed`; `processed_at` records worker completion time when processing settles.
- `memory_revisions` snapshots the memory processing state with `kind_confidence`, `processed_at`, and same-workspace `superseded_by_memory_id` metadata so revision rows preserve the fields that determine current memory lifecycle state.
- `conflicts.status` follows ADR 014: `unresolved`, `auto_resolved`, `admin_resolved`, `merged`, and `kept_both`. `conflicts.resolution_strategy` records auto-resolution strategies such as `rank_then_recency` and `recency_then_source` without locking a larger enum before worker code exists. `conflicts.merged_memory_id` is the structured same-workspace FK for the merged-memory result; `winner_memory_id` remains limited to the source or target memory and is not used for merged results. CHECK constraints keep unresolved rows free of result fields, require winner results only for `auto_resolved`/`admin_resolved`, require `resolved_at` on resolved states, and preserve the existing merged-memory state shape.
- `kind_confidence` is nullable because raw `status='processing'` rows exist before async classification finishes.
- Audit tables use ADR 010 normalized actor and target columns, with `created_at` as the event timestamp name.
- `usage_events` keeps optional `actor_profile_id` and `actor_mcp_key_id` provenance columns in addition to ADR 012 token/model/cost fields. `usage_events.processing_tier` snapshots the tier used for the recorded processing work.
- User-content soft deletion is represented with `deleted_at` on `memories`, `memory_revisions`, `conflicts`, `workspace_tags`, and `memory_tags`; profile removal is represented separately with `profiles.deleted_at`. No RLS hard-delete policies are granted.
- Baseline user SELECT policies require workspace membership through helper predicates that ignore soft-deleted profiles; `profiles` has explicit RLS with an own-profile SELECT policy on `profiles.auth_user_id = auth.uid()` plus an authenticated peer-profile SELECT policy limited to non-deleted profiles sharing at least one workspace with the caller, and no MCP profile exposure. `workspace_members` uses the same active-membership helper so callers can view membership rows across their workspace. Governance/admin-owned surfaces (`conflicts`, `audit_log_memory`, `workspace_invites`, `mcp_keys`, `audit_log_workspace`, and `usage_events`) require workspace admin membership for SELECT. Web/user RLS policies target `authenticated`, and their helper functions explicitly revoke PUBLIC execution and grant only `authenticated`.
- MCP tenant data access uses the dedicated `mcp_session_executor` role, which is `NOLOGIN`, `NOINHERIT`, and non-`BYPASSRLS`. That role alone can execute `set_mcp_session(...)`, is the only role granted the MCP session-validation helper, has only the MCP SELECT grants for `workspaces`, `workspace_members`, `memories`, `memory_revisions`, `workspace_tags`, and `memory_tags`, and has only MCP INSERT on `memories`. `service_role` intentionally has no execute grant on `set_mcp_session`; if backend code uses `service_role` to verify a presented MCP key against `mcp_keys.key_hash`, it must switch to or otherwise run tenant-data work as `mcp_session_executor` before calling `set_mcp_session` or querying RLS-protected MCP data.
- Write RLS is intentionally narrow but present where the spec is explicit: members can insert only their own raw pre-processing memories; validated MCP sessions can insert raw pre-processing memories only with no profile authorship; users can update their own memories; admins can update workspace memories, manage MCP keys, manage invites, resolve conflicts, update workspace settings, and insert/update/delete `workspace_members` rows for membership management. A generic trigger maintains `updated_at` on mutable timestamped tables. A memory trigger blocks MCP updates/deletes and protects system-managed memory columns from regular non-service update paths, while allowing authenticated workspace admins to perform explicit governance corrections only for `kind`, `kind_confidence`, and `deleted_at`, and allowing service/backend contexts for future async processing. A generic trigger prevents `workspace_id` changes on workspace-scoped rows so update policies cannot be used to re-home rows across workspaces. No hard-delete policies are granted for user-content tables.

## ALEX-002 Auth Foundation

- `public.ensure_profile(p_email text, p_display_name text default null)` exists because first sign-in must create a `profiles` row before the user owns any app row that ordinary RLS can reference. ALEX-001 intentionally has no `profiles` self-insert policy, so this "user writes a row they do not yet own" path goes through a scoped RPC instead of weakening table RLS.
- `ensure_profile` is `SECURITY DEFINER` so an authenticated user can upsert only their own profile as resolved by `auth.uid()` inside the function. The function pins `search_path = public, pg_temp`, validates email shape, and returns the resolved `profiles` row. A minimal `profiles.email` column is added by the same migration so the auth callback can sync Supabase Auth email to app identity.
- `ensure_profile` revokes public, anon, service-role, and MCP executor execution before granting execute only to `authenticated`. Route handlers call it through the cookie-backed Supabase client; they do not use `service_role` for profile bootstrap.
- `public.create_workspace_with_admin(p_name text, p_slug text, p_context_description text)` exists because the first workspace insert and first admin membership insert must commit atomically before ordinary workspace-admin RLS can prove authority. It resolves the caller's `profiles.id` from `auth.uid()`, requires Task 3 profile sync to have completed, validates name/slug/context inputs, inserts the `workspaces` row with `tier='basic'`, inserts the creator's `workspace_members.role='admin'` row, writes a matching `audit_log_workspace` row with `action='workspace_created'`, and returns the new workspace id.
- `create_workspace_with_admin` is also `SECURITY DEFINER` with `search_path = public, pg_temp`; execution is revoked from public, anon, service-role, and the MCP executor, then granted only to `authenticated`. Slug uniqueness is surfaced with SQLSTATE `23505`, and route handlers use the cookie-backed user client instead of `service_role` for workspace creation.
- Future flows where a user must write an app row before RLS can prove ownership should follow the same pattern: one narrowly scoped definer RPC, pinned search path, explicit input validation, and grants only to the role that needs the capability.
